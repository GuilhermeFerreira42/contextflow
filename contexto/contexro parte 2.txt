## 🛠️ Aba Número 2: O Centro de Comando Analítico (Master-Detail)

O objetivo desta aba é a **Triagem e Qualificação** de dados em alta velocidade.

### Layout e Estrutura

-   **Componente Base:** `wx.SplitterWindow`. A tela é dividida horizontalmente (Grade no topo, Detalhes embaixo).
    
-   **Painel Mestre (Topo):** `VirtualGrid` (wx.grid.Grid).
    
    -   **Colunas:** `[ID] | [Thumb] | [Título] | [Canal] | [Duração] | [Tags IA] | [Status]`.
        
    -   **Navegação:** Totalmente otimizada para teclado. Ao mover a seleção com as setas, o painel de detalhes atualiza instantaneamente.
        
    -   **Filtro:** Um `wx.SearchCtrl` no topo da grade para busca local por texto (título/canal) e tags.
        
-   **Painel de Detalhes (Rodapé):** `DetailPanel`.
    
    -   **Visualização:** Exibe o **Resumo Executivo** (gerado pela IA) e as **Tags** em formato de "chips" clicáveis.
        
    -   **Ação de IA:** Se o vídeo selecionado não tiver resumo, o painel exibe um botão proeminente: `[Gerar Resumo]`.
        

### Experiência do Usuário (UX)

1.  **Visão Geral:** O usuário escaneia 100 vídeos pela Grid. As tags (ex: #vendas, #tutorial) dão o contexto imediato.
    
2.  **Leitura Rápida:** O resumo aparece no rodapé sem o usuário precisar trocar de aba ou abrir janelas.
    
3.  **Processamento em Lote:** O usuário seleciona múltiplos vídeos (via checkbox) e clica em um botão "Processar Selecionados". O sistema enfileira as chamadas de API e atualiza a coluna "Status" na Grid em tempo real.

## 📖 Aba Número 3: O Laboratório de Imersão (Reader Mode)

O objetivo desta aba é o **Estudo Profundo** e a verificação de fatos.

### Layout e Estrutura

-   **Modo de Leitura:** Layout limpo, centralizado (estilo Notion/Medium), com tipografia focada em longas leituras.
    
-   **Conteúdo:** Transcrição na íntegra. Não haverá edição (CRUDE) nesta fase para evitar corrupção de dados brutos.
    
-   **Barra Lateral (Metadata):** Dados técnicos do vídeo, link original e campo de "Notas Pessoais" (opcional).
    

### Experiência do Usuário (UX)

1.  **Acesso:** O usuário dá duplo clique em um vídeo na Aba 2. O sistema "teletransporta" o usuário para a Aba 3 já com o texto carregado.
    
2.  **Âncoras de Tempo (Timestamp Anchors):** Todo timestamp no texto (ex: `10:15`) é um hiperlink. Ao clicar, o navegador abre o vídeo no ponto exato.
    
3.  **Foco:** Sem distrações de grid ou botões de comando. É o lugar de consumir o conhecimento extraído.

## ⚖️ Veredito de Risco e Viabilidade

1.  **Risco de Performance:** O uso de thumbnails na Grid e a atualização do painel de detalhes por clique exigem que o acesso ao banco de dados seja feito em uma thread separada ou com um cache de memória agressivo. Se você fizer buscas síncronas no SQLite a cada "seta para baixo", a interface vai travar.
    
2.  **Risco de Custo:** A função de "Exportar tudo com resumo" é perigosa. O sistema deve obrigatoriamente avisar: *"Você está prestes a processar 50 vídeos. Isso consumirá aproximadamente X tokens."*
    
3.  **Complexidade:** Você está adicionando uma camada de "Inteligência de UI" (Reatividade). Isso exige que seu `AppState` (PubSub) seja impecável para que a Aba 2 e a Aba 3 não fiquem com dados diferentes.

### Análise de Viabilidade Operacional

1.  **O Dilema do Splitter:** Para implementar isso no `wxPython`, você usará um `wx.SplitterWindow` principal para dividir a Grid do resto. Dentro da metade de baixo, você coloca **outro** `wx.SplitterWindow` para dividir o Resumo do Log.
    
    -   *Vantagem:* O usuário pode esconder o log puxando a barra para baixo, ou aumentar o resumo se estiver em uma leitura profunda.
        
2.  **O Console de Logs como Widget Independente:** Não use um `wx.TextCtrl` comum para o log. Use um componente que suporte cores (como o `wx.stc.StyledTextCtrl`) para que erros fiquem vermelhos e sucessos verdes. Isso ajuda o analista a identificar problemas sem precisar ler cada linha.
    
3.  **Integração com a Aba 3:** Quando o usuário der duplo clique na Grid (Aba 2), o sistema mudará para a Aba 3, que é o "Reader Mode" (Leitor Imersivo) que mostrei no mockup anterior.
    

**Veredito de Risco:** A estrutura agora está completa. O risco agora não é mais de layout, mas de **sincronia**. O `AppState` precisa garantir que, ao atualizar um log de download, a Grid também mostre o progresso.

### 1\. O Comportamento "Resumo Inteligente"

A ideia de a tela abrir apenas se houver conteúdo é excelente. No `wxPython`, isso se chama **Gerenciamento de Visibilidade Dinâmica**.

-   **Fluxo Automático:**
    
    -   O usuário clica no vídeo A (tem resumo) O `SplitterWindow` se expande automaticamente e mostra o texto.
        
    -   O usuário clica no vídeo B (sem resumo) O `SplitterWindow` se fecha (Sash na posição zero), devolvendo todo o espaço para a Grid.
        
-   **Vantagem:** O usuário ganha foco total na planilha quando está apenas organizando e ganha o insight automaticamente quando ele existe.
    

### 2\. Configurações de Comportamento (Menu Ferramentas)

Para que o sistema não seja "irritante" (abrindo e fechando o tempo todo contra a vontade do usuário), as opções que você sugeriu são o padrão ouro:

1.  **Modo Adaptativo (Padrão):** Abre se tiver resumo, fecha se não tiver.
    
2.  **Modo Sempre Visível:** Mantém o painel aberto, mostrando "Aguardando processamento..." caso não haja resumo.
    
3.  **Modo Manual:** O painel só abre se o usuário clicar no botão "Ver Resumo" ou der um comando específico.
    
4.  **Modo Oculto:** Foca 100% na Grid e nos Logs.
    

* * *

### 3\. Integração com o Log do Sistema

Como o Log deve ficar abaixo do Resumo, a hierarquia de controle de visibilidade ficaria assim:

-   **Prioridade 1 (Grid):** Sempre visível.
    
-   **Prioridade 2 (Resumo):** Visibilidade vinculada à existência de dados ou configuração.
    
-   **Prioridade 3 (Log):** Pode ser minimizado para uma "barra de status" de uma única linha ou expandido para depuração.
    

* * *

### 4\. Resumo dos Requisitos Atualizados para a Aba 2

**Experiência do Usuário (UX):**

-   **Navegação Rápida:** O usuário usa as setas. Se o vídeo tem resumo, a tela "brota" embaixo da grid com a análise. Se não, a grid ocupa a tela cheia.
    
-   **Controle de Espaço:** O usuário pode configurar se quer que essa automação aconteça ou se prefere manter o layout fixo.
    
-   **Indicador Visual:** Na Grid, uma coluna de ícones (ou as **Tags da IA**) indica visualmente se o resumo já existe antes mesmo do clique.
    

**Arquitetura Técnica:**

-   **Evento de Seleção:** O gatilho será o `EVT_GRID_SELECT_CELL`.
    
-   **Estado de Visualização:** O `AppState` deve guardar a preferência do usuário (Sempre exibir / Adaptativo / Nunca exibir).
    
-   **Performance:** A verificação "tem resumo?" deve ser feita no cache local (SQLite) para que a interface não dê pequenos "pulos" ou travamentos ao mudar de linha.

# Documentação Técnica: ContextFlow (v0.1.0)

## 1\. Visão Geral da Arquitetura

O ContextFlow é construído sobre uma arquitetura de **Single Source of Truth (Fonte Única de Verdade)**. O sistema utiliza o `AppState` para mediar a comunicação entre a interface (wxPython), o motor de processamento (`Processor`) e a persistência de dados (SQLite).

### Componentes Principais:

-   **`AppState` (Core):** Singleton que gerencia o estado da aplicação em memória e notifica a UI sobre mudanças via padrão Observer.
    
-   **`Processor` (Core):** Gerencia a fila de tarefas (`task_queue`) e orquestra o download de metadados, thumbnails e transcrições em threads separadas.
    
-   **`YouTubeManager` (Services):** Interface de baixo nível para extração de dados do YouTube e validação de URLs.
    
-   **`DatabaseHandler` (Storage):** Camada de persistência que garante que os vídeos processados sobrevivam ao fechamento do app.
    

* * *

## 2\. Fluxo de Dados e Ciclo de Vida do Vídeo

O sistema foi projetado para ser totalmente não-bloqueante, seguindo estas etapas:

1.  **Entrada:** O usuário insere URLs (vídeos ou playlists). O `Processor` resolve as URLs de forma assíncrona (`_async_resolve_urls`).
    
2.  **Fase Temporária (UUID):** Antes de descobrir o ID real do YouTube, o vídeo é registrado no `AppState` como uma `active_task` usando um UUID aleatório. Isso permite que a UI mostre o item imediatamente na fila.
    
3.  **Processamento:**
    
    -   **Metadados:** Identifica ID, Título e Duração.
        
    -   **Anti-Bloqueio:** O motor aplica um *jitter* (pausa aleatória entre 2s e 5s) para evitar banimentos por excesso de requisições.
        
    -   **Persistência:** Assim que o ID é obtido, o `AppState` promove a tarefa de "ativa" para "vídeo persistido" no banco de dados.
        
4.  **Finalização:** A transcrição é salva, o contador de tokens é calculado e o `AppState` remove a tarefa da lista de downloads ativos, notificando a UI para atualizar a visualização final.
    

* * *

## 3\. Identidade Visual e Layout (Tema Escuro)

Diferente de mockups tradicionais, o ContextFlow utiliza um **Dark Theme** nativo definido em `constants.py`:

-   **Background:** `(30, 30, 30)`
    
-   **Foreground:** `(220, 220, 220)`
    
-   **Accent (Destaque):** Azul `(0, 120, 215)`
    

* * *

    2.  **Foco no Analista:** Implementar filtros complexos, busca avançada em transcrições e visualização de dados (Nuvem de Palavras).
